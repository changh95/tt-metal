I'll write structured prose with short headed paragraphs.</think>A log-structured merge-tree turns random writes into sequential ones by buffering updates in memory and periodically writing them out as immutable, sorted files. LevelDB, RocksDB, Cassandra and ScyllaDB are all built on this idea, and although their details differ, the core mechanics are the same.

**The write path.** When a client writes a key-value pair, the engine first appends the record to a write-ahead log on disk. The log is purely sequential, so the append is cheap, and it provides durability: if the process crashes, replaying the log rebuilds the in-memory state. The record is then inserted into the memtable, an in-memory sorted structure that is usually a skip list or a balanced tree. Deletes take the same path: instead of removing anything, the engine writes a special marker called a tombstone. Once the memtable reaches its configured size, typically a few tens of megabytes, it is frozen and a fresh memtable takes over new writes. A background thread then writes the frozen memtable to disk as a sorted string table, or SSTable. Because the memtable is already sorted, the flush is a single sequential write, after which the corresponding part of the write-ahead log can be discarded.

**The read path.** Reads are more involved, because the newest version of a key may live in several places. The engine checks the active memtable first, then any frozen memtables that are still being flushed, and finally the SSTables on disk from newest to oldest. The first version it finds wins; if that version is a tombstone, the key is reported as missing. Each SSTable carries a sparse index of its data blocks, so a lookup inside a file needs only a binary search over the index followed by a single block read, and that block is often already in the block cache. Range scans merge iterators over the memtables and all relevant SSTables, which is efficient precisely because every source is sorted.

**Compaction.** Without further work, the number of SSTables would grow without bound and every read would have to consult more and more files. Compaction is the background process that merges SSTables, drops overwritten values and expired tombstones, and keeps the structure shallow. Two families of strategies dominate. Size-tiered compaction groups files of similar size and merges them once enough have accumulated, producing a larger file in the next tier. Each byte is rewritten relatively few times, so write amplification is low, but several files may cover overlapping key ranges at any moment, which raises read amplification and can temporarily require a lot of free disk space. Leveled compaction, popularized by LevelDB, organizes files into levels whose total size grows by a fixed factor, commonly ten. Within every level below the first, files have non-overlapping key ranges, so a point lookup touches at most one file per level. The price is higher write amplification, because data is rewritten each time it moves down a level and must be merged with the overlapping files it meets there. Many production systems use hybrids, for example tiering the upper levels and leveling the lower ones, to balance these costs for a particular workload. Whatever the strategy, compaction has to keep up with the incoming write rate: if it falls behind, files pile up in the first level, reads slow down, and engines such as RocksDB eventually throttle or stall writes until compaction catches up, so reserving enough background I/O bandwidth matters as much as choosing the strategy itself.

**Bloom filters.** Even with leveled compaction, a lookup for a key that does not exist would otherwise probe every level. To avoid this, each SSTable stores a Bloom filter over its keys: a compact bit array that answers either "definitely not present" or "possibly present". With about ten bits per key the false-positive rate is roughly one percent, so the vast majority of unnecessary disk reads are skipped. Bloom filters do not help range scans, which is why some engines add prefix or range filters for those queries.

**Putting it together.** The appeal of the design lies in its trade-offs. Writes are fast and sequential, flash devices are spared from small random writes, and the data on disk compresses well because the files are immutable and sorted. The costs are read amplification, write amplification and space amplification, and tuning an LSM-tree engine is largely a matter of deciding where on that triangle a workload should sit. The memtable size, the level size ratio, the compaction strategy and the number of Bloom filter bits per key are the main knobs, and understanding how each of them shifts the balance is the key to operating these systems well.<|endofturn|><|endoftext|>
